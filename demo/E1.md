# E1 demo

From the checkout root, install the pinned workspace dependencies with `pnpm install --frozen-lockfile` and supply private configuration in `demo/.env`.

```sh
pnpm demo --check       # read-only prerequisites (also the default)
pnpm demo --payments    # one x402 purchase and one sandbox SEPA order
pnpm demo --run         # full interactive story, including owner actions
```

Payment modes send testnet transactions and sandbox payout orders. The full mode requires a terminal: the owner performs mandate, top-up, budget adjustment, revoke and sweep actions in their existing dashboard/scripts, then supplies transaction hashes. The orchestrator verifies those references and state. It does not hold owner credentials or claim that a software P-256 owner CLI is a browser passkey tap. Owner Safe scripts support USDC sweep; EURe uses the configured relayer.

The command stops on unexpected results and returns nonzero. `--payments` is only a milestone and its evidence has `complete: false`. Full live acceptance has not yet been demonstrated.

## Private configuration

Required for preflight and payment modes:

- `MANDATE_CONTRACT_ID`, `AGENT_ID`, `AGENT_NEAR_PRIVATE_KEY`, `AGENT_EVM_ADDRESS`, `SAFE_ADDRESS`.
- `NEAR_RPC`, `BASE_SEPOLIA_RPC` optionally override the public testnet defaults.
- `E1_SELLER_URL`, `MCP_SELLER_ORIGINS`, `E1_X402_MAX_UNITS` (maximum USDC base units). The ceiling is checked against fresh requirements at signing, as well as in preflight.
- `E1_SUPPLIER`, `E1_IBAN`, `E1_IBAN_SALT`, `E1_SEPA_AMOUNT` (euros, at most two decimal places), `E1_INVOICE_ID`.
- `M1_URL`, `M1_AGENT_TOKEN`, `E1_DASHBOARD_URL`.
- `NEAR_AI_API_KEY` is optional; absence is reported as skipped. Presence does not prove inference works. Keep scamcheck's own local environment consistent with these settings.

Additional full-run configuration: `SUBMITTER_ACCOUNT_ID` for owner NEAR transaction lookups; `E1_TOPUP_USDC_UNITS` and `E1_TOPUP_EURE_UNITS` for exact Safe transfer amounts; distinct sandbox-only `E1_ATTACK_IBAN` and unapproved `E1_ATTACK_PAY_TO`. All modes expect an already provisioned mandate and supplier. Read-only and payment-only checks require sufficient agent float. Full mode instead checks that the Safe can fund each planned top-up, that the resulting agent balance covers the purchase and stays within its mandate float cap, then requires funded agent balances after the owner actions. The owner demonstrates a fresh mandate transaction and fresh top-ups during the run.

Start SE1, M1 and the dashboard using their own package runbooks. M1 must run this revision's authenticated `GET /health/<agent>` endpoint. Health verifies the agent token and public deployment binding; it does not authenticate with Monerium or certify its credentials. Monerium credentials stay in M1. Only sandbox/fixture IBANs and testnet identities are permitted. Never paste private values into chat or commit them.

## Evidence and failure recovery

The demo records only selected request/transaction/order references, fixed outcome descriptions and a digest of the returned resource under `demo/evidence/e1-<run>.json`. Raw resource content, IBANs, salts and credentials are excluded. A submitted Monerium sandbox order is not bank settlement. x402 completion requires matching authorization and token-transfer events, plus resource delivery. Safe transfers are checked against token, sender, recipient and amount and must postdate the run's starting block.

Each child MCP process uses a fresh private receipt directory under `demo/.runs/<run>/receipts`. It exposes A2's four tools but has no background held-payment resumption timer. The dashboard may display held items; this demo never resumes them automatically.

A per-agent `.e1-<identity-hash>.lock` is created before payment execution and retained on failure. Inspect the existing run's evidence, private MCP receipts, NEAR reservations and M1 order records before manually removing a retained lock. Never treat a timeout as permission to repeat a business payment. Successful payment-only runs remove their lock but still consume the invoice ID.

The budget demonstration requires a real pending reservation. It verifies pending state at the second request's failed execution block, using a finalized transaction receipt; an older final-state snapshot cannot stand in for this evidence. If MPC finishes too quickly, historical state is unavailable, or the budget period rolls over, the run stops rather than claiming success. It does not simulate latency. The owner can revoke and sweep separately after any failed run.

## Verification limits

Local regression tests cover prerequisite validation, the signing-time ceiling, receipt-directory isolation, evidence filtering, and block-bound pending proof. M1 tests cover the authenticated read-only endpoint. These are not live payment evidence. A configured fresh-clone full run, owner acceptance, lead-assigned PR review and required CI remain outstanding.
